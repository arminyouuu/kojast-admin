🧱 MVP SPECIFICATION (V2) — “Kojast”
🌀 Purpose
A mobile and web system that helps users discover shops, cafés, restaurants, gyms, and public places across their city.

Admins manage all listings through a dedicated dashboard, while end users explore categorized content smoothly through the Flutter app.

The platform prioritizes simplicity, scalability, and clean layered architecture across both backend and frontend.

1. PRODUCT SCOPE
🎯 Primary Objective
Deliver a two‑faced MVP system:

Public app (Flutter): allows users to browse and explore places with images, categories, descriptions, and addresses.
Admin dashboard (Web): enables authorized admins to create, read, update, and delete both categories and places directly through a friendly interface.
🔹 Target Users
City residents & travelers discovering locations.
Verified admins assigned by the system operator.
🔹 Technology Foundation
Frontend Mobile: Flutter
Frontend Web (dashboard): Web interface tied to same API
Backend: Node.js REST API
Database: MySQL (relational)

📍 3.2 Places
Each record describes a single location.

Data Model Fields

Field	Type	Description
id	Integer	Unique identifier
name	String	Display name
description	Text	Short summary
address	String	Physical address visible to user
categoryId	Integer	Category relation
latitude / longitude	Float	Geo coordinates
images	Array of strings	URLs of all images for gallery
createdAt / updatedAt	Datetime	Automatic timestamps
🧠 3.3 API Features
Endpoint	Method	Description
/categories	GET	List all categories.
/places	GET	List or filter places. Accepts categoryId, page, limit.
/places/:id	GET	Fetch single place including all images.
/admin/categories	POST/PUT/DELETE	CRUD operations for categories (restricted).
/admin/places	POST/PUT/DELETE	CRUD operations for places (restricted).
Pagination Parameters:

page: current page number (default = 1)
limit: number of items per page (default = 10)
Returns metadata { total, page, pages }
Lazy Loading in app:

Flutter triggers next page when the user scrolls near the end of current data.

Responses:

All objects returned in JSON with image arrays; errors follow:

Gives administrators direct CRUD control over content with structured authorization.

5. BACKEND ARCHITECTURE (Three‑Layer Model)
Layer	Responsibilities
Presentation Layer	HTTP routing, request validation, authentication middleware for admin routes, JSON response handling.
Application Layer	Business logic — pagination, filtering, category logic, data validation.
Data Layer	Direct database interaction (ORM/queries), entity models for Place, Category, PlaceImage.
Relations

Category 1→N Place
Place 1→N PlaceImage
Entities Overview

Place: id, categoryId, name, description, address, latitude, longitude, timestamps

12. LIMITATIONS (FOR MVP)
No role‑based multi‑user system beyond basic admin.
Auth optional; may rely on static admin credentials in config.
No upload mechanism yet; dashboard expects direct image URLs.
Geolocation features inactive (coordinates stored only).
Basic paginated search only (no fuzzy search).
